Invoice Questionnaire

Design spec for the guided intake that produces a finished Trilogy invoice with minimal manual entry.

§ 1 — Purpose

PMM Construct replaces the manual process of building a Trilogy invoice in Word. Instead of typing every line item by hand, the user answers a short guided questionnaire and — for the Trilogy Partners invoice — uploads the subcontractor invoices for the draw. Construct extracts the data, builds the line items, applies the standing fee, and outputs the finished invoice.

Two invoice types are supported, and they behave differently:

Invoice typeFeeNumbered bySource of line items
Trilogy DesignWorks Trilogy DesignWorks Administration and Supervision — 20%, auto-calculated from this invoice Invoice # Entered manually
Trilogy Partners No calculated fee on the invoice. The GC Fee is a line item; amount = % × base $ Draw # Uploaded subcontractor invoices
§ 2 — Design Principles
  1. One question per screen, with sensible defaults. The user should be able to tab through quickly. Anything that can be pre-filled, is.
  2. Never ask twice. Company address, fee rates, and remittance details are constants — they are configuration, not questions.
  3. Upload-first for Partners draws. The fastest path is "drop the sub invoices in," not "type each line." Typing is the fallback, not the norm.
  4. Every extracted value is reviewable and editable. OCR and PDF parsing are never trusted blindly. The user confirms before the invoice is final.
  5. The math is never the user's job. Line totals, the fee, the GC Fee amount, and the balance are always computed.
§ 3 — Questionnaire Flow

Step 0 — Invoice type

Which invoice are you creating? ( ) Trilogy DesignWorks   ( ) Trilogy Partners

This single choice branches everything downstream: which logo, which fee label and rate, whether the number field is "Invoice #" or "Draw #", and whether the upload step appears.

Step 1 — Client / project

Who is this billed to? Client or project name → fills the Bill To field.

Step 2 — Invoice / Draw number

What is the invoice number? (DesignWorks) or Which draw is this? (Partners)

Step 3 — Date

Invoice date? Defaults to today; user can change.

Step 4 — Line items

DesignWorks path — manual entry:

Add the line items. Quantity, Description, Rate. Amount auto-fills as Qty × Rate; user can type it directly on rows where Rate isn't a true unit price.

Partners path — upload to populate:

Upload the subcontractor invoices for this draw. Drag-and-drop zone. Accepts PDF and image/scan (JPG, PNG, HEIC). Whatever a sub sends arrives as a PDF or a photo and is uploaded the same way.

Each uploaded sub invoice becomes ONE line on the Trilogy invoice — matching how the real Trilogy Partners invoice bills (one line per sub, e.g. "Timberline Porta Potty — November"). Construct does NOT re-type the sub's own itemization onto the Trilogy invoice; instead the original sub PDF is kept and appended to the final packet as backup (see Step 6).

For each uploaded PDF, Construct extracts and presents for review:

  • Description — vendor name + purpose, pre-filled, fully editable
  • Amount — the detected invoice total, editable
  • Source confidence — high for a clean text-based PDF, low for a photo or scan that needs OCR

Total detection uses labeled-total-first (scan for "Balance Due", "Total", "Amount Due"), falling back to the largest dollar amount if no labeled total is found. A collapsible raw extracted text panel on each row lets the user verify a low-confidence guess.

The user reviews each row, corrects anything wrong, and can add:

  • A manual line for items with no document (e.g. "Supervision Fee November").
  • A GC Fee line — a special manual line with four structured reference fields (month, year, %, base $) that assemble the description. The amount auto-calculates as % × base $.

Step 5 — Fee

The two invoices handle the fee in fundamentally different ways.

DesignWorks — calculated fee step. "Trilogy DesignWorks Administration and Supervision" at 20%. This is a percentage of the invoice being created, so Construct calculates it: the user supplies the fee base (and can fill it with the line-item total in one click), and Fee = base × 20%. DesignWorks has a dedicated Fee step.

Partners — no separate Fee step. Trilogy Partners has no separate fee step in the questionnaire. The "GC Fee" is a line item, added from the upload step like any other line ("+ Add GC Fee line"). It carries four structured reference fields — month, year, percentage, base $ — which assemble the description in this exact format:

GC Fee for the period September 2025 14% of $73954.76

The fee amount auto-calculates as percentage × base $. Because this matches how the real invoice is computed (the % and base $ values published in the description are the source of the amount), Construct does the math automatically and the GC Fee line sums into the Balance Due like any other line item.

Step 6 — Review & generate the packet

Here's your invoice. Anything to fix? Full preview: header, every line item, fee row (if any), and the auto-summed Balance Due. Edit-in-place on any field.

For a Trilogy Partners draw, "Generate" produces an invoice packet, not a single page:

  1. The Trilogy Partners invoice page.
  2. An index / divider page listing every sub invoice in the packet — line number, vendor, source filename, and the packet page it starts on — so it works as a table of contents for the backup.
  3. Every uploaded subcontractor invoice PDF, appended behind the index in invoice line-item order so a reviewer can move line-by-line to the matching backup.
  4. Each appended sub page is lightly stamped in the top margin with its line number and vendor (e.g. "Line 3 — Timberline Porta Potty"), and the whole packet carries a footer page number so the index's page references stay accurate. The stamp is an overlay; the sub's original document content is never modified.
  5. Manual lines and GC Fee lines have no backup page and are not listed on the index.

A Trilogy DesignWorks invoice generates as a single page — it has no uploaded sub invoices to append.

Packet assembly is a server-side step (assemble_packet.py); a browser-only tool cannot merge real PDF files. The prototype's "Generate" button produces the invoice page; in production this is one step in the full packet workflow.
§ 4 — Configuration, not Questions

These are set once in PMM Construct settings and never asked:

  • Company addresses, phone, email, websites (both entities)
  • Logos (both entities)
  • Standing fee: DesignWorks 20% (Partners has no calculated fee)
  • DesignWorks fee label: "Trilogy DesignWorks Administration and Supervision"
  • Default table layout (11 line rows + fee row + balance)
  • Packet assembly rules: invoice first, index page, subs in line order, stamped
§ 5 — Extraction Scope

The Partners upload step relies on extracting two things from each sub invoice: vendor name and total amount. Both are heuristic; both are reviewable.

Vendor name: the first non-empty line of the document that isn't a dollar amount and isn't the word "Invoice." Falls back to the filename, cleaned up.

Total amount: labeled-total-first ("Balance Due," "Total," "Amount Due"), falling back to the largest dollar amount on the page. The chosen basis is shown to the user so they can sanity-check.

Confidence levels:

  • High — text-based PDF with a clearly labeled total ("Balance Due: $247.12").
  • Review — text-based PDF with no labeled total; largest-amount fallback was used.
  • Low — please check — OCR result, no text layer, or unparseable. The user must verify.

Every row exposes a collapsible "raw extracted text" panel so a low-confidence guess can be checked against what was actually on the page.

§ 6 — Build Phasing
  1. Phase A — Questionnaire + manual entry + PDF output. Built. Proves the flow; already beats the Word process.
  2. Phase B — PDF text extraction. Built. Text-based sub invoices parsed with pdf.js; vendor + total extracted by heuristic.
  3. Phase C — OCR for scans and photos. Built. Scanned PDFs and photos run through Tesseract OCR (ocr_sub_invoice.py): image is pre-processed (grayscale, autocontrast, upscale, sharpen), text is recovered, and the same vendor/total heuristics from Phase B are applied. OCR results are always flagged low confidence — the tool produces a head start, never a final answer.

Remaining work for the production app: wire the three extraction paths (manual / pdf.js / OCR) behind one upload step, persist drafts, and run extraction server-side so OCR is fast and the packet merge and OCR live alongside the questionnaire.
