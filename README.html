PMM Construct

Invoice management for Trilogy — part of the PMM Tools Suite.

PMM Construct turns the manual process of building a Trilogy invoice in Word into a guided workflow: answer a short questionnaire, upload the subcontractor invoices, and get back a finished, branded invoice — with the supporting documents assembled into one packet.

This repository holds the working prototype, the supporting tools, and the design spec.

The Two Invoices

PMM Construct produces two invoice types, and they behave differently:

AspectTrilogy DesignWorksTrilogy Partners
Numbered byInvoice #Draw #
FeeAuto 20% Admin & SupervisionNo calc GC Fee as line item
Line itemsEntered manuallyOne line per uploaded sub invoice
OutputSingle-page invoiceInvoice + index + appended sub invoices

The DesignWorks fee is calculated from this invoice's line items. The Partners "GC Fee" is computed from all project invoices, so it cannot be derived from this one alone — it enters as a normal line item with structured reference fields (month, year, %, base $) that assemble the description; the amount is the product of % × base $, auto-calculated.

How the Pieces Fit
┌──────────────────────────┐ │ Questionnaire │ │ (the prototype .jsx) │ └────────────┬──────────────┘ │ uploaded sub invoice PDFs / photos │ ┌────────────────────┼────────────────────┐ │ │ │ text-based PDF scanned PDF / no document → pdf.js in the photo → OCR → typed manually prototype (ocr_sub_invoice.py) │ │ │ └────────────────────┼────────────────────┘ │ one editable line per sub invoice (vendor + purpose, detected total) │ ┌────────────┴──────────────┐ │ Generate the packet │ │ (assemble_packet.py) │ └────────────┬──────────────┘ │ Trilogy invoice + index page + stamped subs

Extraction has three paths — typed, parsed, OCR'd — and all three feed the same one-line-per-sub review. Every extracted value is editable and carries a confidence flag; nothing is ever auto-finalized.

Running the Tools
Prototype

A React component. The site/ folder is a minimal Vite app that wraps it.

cd site
cp ../pmm-construct-prototype.jsx src/
cp ../eagle_light_font.js src/
cp ../logos.js src/
npm install
npm run dev

For deployment, the GitHub Actions workflow stages those files automatically on every push to main.

Packet Assembler
pip install -r requirements.txt
python assemble_packet.py manifest.json output_packet.pdf

The manifest lists the invoice PDF and sub invoices in line order. Output: invoice page, index/contents page, then every sub invoice appended in line-item order with a stamp identifying its line and vendor.

OCR Tool
# Requires the Tesseract binary:
#   Ubuntu/Debian:  sudo apt-get install tesseract-ocr
#   macOS:          brew install tesseract
pip install -r requirements.txt
python ocr_sub_invoice.py scanned_invoice.png result.json

Outputs the vendor and total recovered from the image, plus the raw OCR text, in the same shape the prototype's review step consumes. Always flagged low-confidence — OCR is a head start, not a final answer.

Live Prototype Demo

The prototype is published to GitHub Pages automatically. The site/ folder is a small Vite app that wraps pmm-construct-prototype.jsx, and .github/workflows/deploy.yml builds and deploys it on every push to main.

One-time setup: in the repo, go to Settings → Pages → Build and deployment → Source and select GitHub Actions. After the next push (or a manual run from the Actions tab), the prototype is live at https://<your-username>.github.io/<repo-name>/.

What GitHub Pages can and cannot host

GitHub Pages serves static files only — it does not run Python.

  • The prototype demo, the spec, this README, and the fillable PDFs are all served fine.
  • The two Python tools (assemble_packet.py, ocr_sub_invoice.py) cannot run on Pages. They are backend tools — in the real PMM Construct app they run server-side, where OCR is faster and the PDF merge has the file access it needs.

This repo is the home for the code and documentation; Pages hosts the live prototype demo; and the Python tools run wherever PMM Construct's backend lives.

Honest Status
This is a prototype plus working tools, not a finished product.

Works now: the questionnaire flow, real PDF text extraction, real OCR, the packet assembler, the brand-correct generated invoice PDF, both fillable PDFs.

Extraction is assistive, not automatic. Heuristics guess the vendor and total; OCR results are always low-confidence. The review step and the raw-text panels exist because a person must confirm every figure. This is by design — it is a head start, not an answer.

Not built yet: integrating the three extraction paths behind one upload step in a deployed app, draft persistence, and running extraction server-side. That is the production engineering step.

See PMM_Construct_Spec.html § 6 for the full build phasing.
